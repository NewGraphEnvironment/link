# Task: Backlog move 14: Primitive tables in one shape, and a parallel publish (#499)

**If we do it:** every host's database holds `cabd.dams` in one column layout, so a fresh cloud host passes the host-parity pre-flight, and a province-wide publish takes minutes rather than about 53. **If we never do:** a run with a newly built cloud host is refused before any write ("hosts hold different snapshot primitives"), and each full publish spends most of an hour putting objects one at a time.

Batches: 21 (#494, primitive tables load in one shape) and 22 (#488, publish in parallel; #334, the public read). One phase per batch, one PR. `/gh-pr-merge` ticks move 14 on merge.

## Decided at the gate

The owner answered the four gate questions at the resume (2026-11-22), each with its recommendation: **1a** (the reload layout, `ogc_fid, geom, <attributes>`), **2a** (a PSOCK worker pool in R over `put-object`, `LNK_PUBLISH_JOBS` default 8), **3** (#334's public read not ready; #334 stays open and its body says why), **4a** (measure on two scratch prefixes in fresh-bc, every version removed after). The full text of each option stays under `## Open decisions (answered 2026-11-22)` below.

A synchronous Plan review ran before the baseline (`planning/active/review-plan.md`, 1 blocker, 12 findings, all folded). It changed Open decisions 1, 2 and 4 and both phases: the scratch measurement on two prefixes, the pool as a PSOCK cluster with every result checked, listed rather than per-key ETags and versions, the proof widened to column types and `ogc_fid`, and `cabd_load()` taking its tables as arguments.

Settled by reading the code, not owner forks:

- **PSCIS has no create-versus-reload difference by construction.** `bc2pg_load()` (`data-raw/snapshot_bcfp_lib.sh:126`, `:144`) drops each view's table before every attempt and before the WFS fallback, so every load creates the table. Phase 1 confirms it with two loads; the bc2pg-against-WFS-fallback content difference is already documented there and stays.
- **The other primitives are one shape already.** `fresh.modelled_stream_crossings` loads with `-overwrite` and no `OGR_TRUNCATE` (ogr2ogr drops and recreates), and is identified by its S3 `VersionId`, not content. `bcfishobs.observations` is `DROP` + `CREATE` with a fixed column list + `-append`. Only `cabd.dams` takes the truncate path (`--config OGR_TRUNCATE YES`, `data-raw/snapshot_bcfp.sh:240-248`).
- **The content md5 itself does not change** (`.lnk_table_content_md5()`, `R/lnk_artifact.R:560`): option 2 of #494 (an order-independent md5) re-keys every recorded md5 and was not recommended by #494's own decision (owner, 2026-11-17: option 1). `R/lnk_artifact.R` is not edited at all, not even its doc comment: the comment is accurate, and the file is mapped `any` in `data-raw/pretest_inputs.csv:3`, so a comment edit would force the pre-run gate (Plan review).
- **PUBLISH helpers go in the existing `R/lnk_publish.R`,** mapped `none` in `pretest_inputs.csv:93`. A new `R/` file would need a mapping row, or `test-pretest.R` fails (Plan review).
- **`R/lnk_scenario_export.R` is not touched:** the issue's "version-id reads" there do not exist. The reads are in `data-raw/habitat_publish.R:170-182`, `:247-262` (Plan review).

## Open decisions (answered 2026-11-22: 1a, 2a, 3 not ready, 4a)

1. **Which `cabd.dams` layout becomes the standard (#494).**
   - **(a) Recommended: the reload layout, `ogc_fid, geom, <attributes>`.** Load into a staging table that is always created fresh, then rebuild `cabd.dams` from it with `geom` second, the attribute list read from the staging table (not hard-coded, so a new CABD field passes through). What this buys: hosts already in the reload layout (the published run's dispatcher held `6f7f44c0…`) agree with hosts on the new code without a forced reload, and recorded md5s (`provenance.source_artifact`, each build's `log_input`, an export's snapshot key) stay valid while CABD returns the same features. Any new or changed dam re-keys `cabd.dams` under either option. This holds only if Phase 1 shows the rebuilt table's text form and column types equal the reload layout's on the same features.
   - (b) The first-load layout (drop `cabd.dams` before each load). Simpler, but every host and every downstream check reads `cabd.dams` as changed once against the published records (`lnk_downstream_load()`'s "differs", an export's snapshot).
2. **How PUBLISH goes parallel (#488).**
   - **(a) Recommended: a bounded worker pool in R over the existing `aws s3api put-object` calls** (`LNK_PUBLISH_JOBS`, default 8), keeping each put's `--content-md5` and the provenance files' `--if-none-match "*"`. Each put asks for `--query '[VersionId,ETag]' --output text`, so its reply is read the way `version()` reads `head-object` today and refused when the VersionId is empty, `None` or `null`. The pool is a PSOCK cluster (`parallel::makePSOCKcluster()`), not `mclapply`: the refusal gate opens a duckdb connection before any put (`R/lnk_publish.R:69`), and forking after a multithreaded library has loaded can deadlock. `parallel` joins `Imports`. Existence and ETag checks before the puts come from paged `list-objects-v2` calls (current objects only); the version ids of unchanged per-group parts come from `list-object-versions` filtered to `IsLatest` with delete markers excluded, scoped to the per-group prefixes. That listing grows with every publish until #334's keep-the-last-N rule exists. The cost is per process (about 2.4 s per object whatever its size), so fewer and concurrent processes both count.
   - (b) The AWS CLI's own transfer (`aws s3 cp --recursive` / `sync`, 10 concurrent requests). Fewer lines, but it drops the per-object `--content-md5` against the manifest's md5 and the write-once `--if-none-match`, so integrity and write-once would need a check after the upload.
3. **#334's public read.** **Recommended: not ready; #334 stays open on it.** It is an infrastructure change (one `public_read_prefixes` entry in fresh-bc and a tofu apply, plus `s3:GetObjectVersion` for every reader) that waits on the account's budget and anomaly alerts. This PR edits #334's body to say batch 22 left it open and why, and changes no code for it. The alternative is that the alerts are in place and the owner wants the read opened now: then it is a change in the infrastructure repository, on the owner's word, and #334 closes when it is applied.
4. **Where Phase 2 measures the parallel publish.**
   - **(a) Recommended: a scratch prefix in fresh-bc** (private, versioned like `habitat/`). The same built root goes to two prefixes, `s3://fresh-bc/scratch/link499/serial/` from main and `.../parallel/` from this branch. A second publish to one prefix would skip every file and per-group part already there (`habitat_publish.R:198-208`, `:228-233`) and time nothing (Plan review blocker). Every version under `scratch/link499/` is removed after, which needs `s3:DeleteObjectVersion` on the operator's credentials.
   - (b) No bucket write in this PR: measure only at the next real PUBLISH (the operator's word), and owe the number.
