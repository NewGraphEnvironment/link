## Findings

- **[fragile]** `data-raw/logs/variant_cost_404/README.md:396-399` and `CLAUDE.md:12` ("about 57 min on a 13-variant ladder") — the parallel-bound arithmetic counts one pass too many. `data-raw/habitat_score/variants_331.csv` has 13 rows including `default`, so the ladder is 12 rungs plus the `default` pass, and `13 × (5.6 + 0.6) + 6.8 + 0.8` counts 13 rung passes and the `default` pass (14). On the measured numbers it is `12 × 4.0 + 5.0 = 53` min saved of about `12 × 6.2 + 7.6 = 82` serial. The headline (digests ruled out, parallel groups is the change) does not move; the two numbers do.
- **[fragile]** `CLAUDE.md:18` ("`--step=bundles` was broken on `main` since #364") and `NEWS.md:7` ("`--step=bundles` works again") — understates what was broken. The md5 self-check of `write_thresholds()` is top-level (`habitat_variants_build.R:347-357`), ahead of the `--step` branch at line 996, so on `main` since `1ae0c34f` (#364 quoted `"model"` into `default`'s CSV) every invocation with `--base=default` stopped at load: `base`, `variants` and `all`, not only `bundles`. A reader of the status entry would conclude the base and variant runs on `main` were fine; this branch's base build is the first the harness could have made since #364.
- **[fragile]** `data-raw/logs/variant_cost_404/README.md:346` — the full variants build is tabled as exiting at `20:36:26` UTC; `launch_state.txt:15` records `2026-10-28T20:36:35Z`. Transcription. In the same table the column headed "wall" holds the script's own "done in" minutes (69.6, 0.8, 13.8) rather than launch-to-exit (70.1, 1.2, 14.3 from the recorded boundaries); the ~0.4 min gap is R start, `load_all()` and connect. Harmless to the measurement, wrong as a column label.
- **[fragile]** `data-raw/logs/variant_cost_404/analyze.R:470-484` — a pass that appears in two logs is resolved by "last wins", where "last" is `list.files()` order (alphabetical by name) then line order, not time. It is right for this directory (`build_preflight_revl.log` sorts before `build_variants.log`) and, in this data, REVL's two logged totals are identical (0.3 / 0.3 for both variants), so the record is unaffected. But the comment says "the last line for a pass wins (REVL is re-run by the full pass after the pre-flight…)", which is a claim about time that the code does not implement: a later re-run of one group logged to a file sorting before `build_variants.log` (say `build_again_revl.log`) would have its fresh timing rows (replaced in `variant_timing.csv`) checked against the older log's total, and since the two runs of a pass are close, the `max(2 %, 0.05 min)` tolerance would usually pass it. That is the "guard that fails toward pass" shape. Keying on `built_at` from the timing row against the log line's own timestamp, or on log mtime, would make "last" mean last in time. Low: a one-off analysis script in a campaign directory, and the committed outcome is correct.

No bug, security or data-loss issue found in the code paths; the four items above are documentation numbers the data does not quite support and one ordering assumption stated in a comment but not implemented.
