# Task: Break streams at a fish observation only where "observed upstream" changes: the top observation per species per line (#396)

## Problem

`lnk_pipeline_break()` cuts the network at every observation position (`<schema>.observations_breaks`, the first break source), as bcfishpass does. #326 (v0.69.0) reduced the gradient breaks to the places a present species' access changes; observation breaks were left as they were.

Only one thing reads an observation break: `access_<sp>` code 2, "accessible, and the species is observed upstream" (`R/lnk_pipeline_access.R`), against code 1, "accessible, not observed upstream". Barrier lifts count observations point against point (`fwa_upstream`, `lnk_barrier_overrides()`), so they need no break. Neither the mapping code (`accessible` comes from the barrier flags, `R/lnk_pipeline_mapping_code.R`) nor the habitat gate (`access = 0` against `> 0`) tells 1 from 2.

Two costs follow from cutting at every observation:

- **Speed.** Every observation position is a cut, so a well-surveyed stream is cut many times. Segments drive the cost of classify, access, the recompute and the persisted tables.
- **Gradient accuracy.** A segment's gradient is computed from its own geometry (`fresh::frs_col_generate()`), so a short segment reads a noisy gradient. A habitat-threshold tuning study measured the effect at fish-sampling sites: on its stream branch 86 % of visits that caught fish sit on a segment starting at the visit, against 10 % of empty ones; the median segment is 113 m long for visits with fish and 305 m for empty ones. So the gradient a rule is applied on at a site depends on whether fish were found there.

## Context

`lnk_pipeline_break()` cuts the network at every observation position (`<schema>.observations_breaks`, built by `.lnk_pipeline_break_obs()` in `R/lnk_pipeline_break.R:144` as `SELECT DISTINCT blue_line_key, round(drm) FROM <schema>.observations`). #326 reduced the gradient breaks to where a present species' access changes; observation breaks were left alone. Only `access_<sp>` code 2 ("observed upstream") reads an observation break, and on one stream line that flag flips once per species, at the species' farthest-upstream observation. Cutting everywhere else costs segments (speed) and makes a site's gradient short-reach *because* fish were recorded there.

**What exploration settled (shapes the phases):**

- **Code 2 is read at segment resolution, and the reduced breaks change it in one countable direction.** `lnk_pipeline_access()` walks `<schema>.observations` (every observation, not the breaks table) with `frs_network_features(direction = "upstream", include_equivalents = TRUE)` (`R/lnk_pipeline_access.R:207`); `fwa_upstream` reads a same-line feature as upstream of a segment when its measure is above the segment's start or within 1 m of it (fwapg `schema.sql`, tolerance 1 from `fresh/R/frs_network_features.R:231`), tributaries by ltree. So the breaks table can shrink while the access input stays whole, and below a species' top and above it nothing moves. **The exception (plan review, verified):** an AFTER segment that starts at species X's kept top and swallows a removed break more than 1 m above it reads X = 2 along its whole length, where the BEFORE piece above the removed break read 1. Only 1 → 2, never 2 → 1, and never 0 ↔ {1, 2} (`blocked` comes from barriers). That is the issue's option 2 at the scale of one merged piece; Phase 1 counts it and Phase 4 accepts it only on segments starting at a kept top. The recompute (`R/lnk_access.R`, always merge) passes `observations = NULL` and **preserves** the prior 2, so what ships keeps code 2 today.
- **Nothing in this repo tells 2 from 1.** Every reader uses `access IN (1, 2)` or `> 0`: `lnk_rollup_wsg.R:120`, `lnk_compare_rollup.R:232`, the validator (`not_accessible` = not 1 or 2), `parity_crosssection.R:203`, `query_habitat_thresholds_mad.R:201`, `wsg_vignette_data.R:124`; mapping code reads `has_barriers_<sp>_dnstr`; the export (`lnk_scenario_export.R`) reads flags and `access_gradient_max` only. No `.qml`/`.sld` is in the repo. Beyond it (plan review, to confirm in Phase 1): the sibling repos' QGIS styles read bcfishpass's text `model_access_<sp>`, not link's integer; bcfishpass's own rollup sums `access_<sp> = 2` km (`length_naturallyaccessible_obsrvd_<sp>`), the one reader anywhere that tells 2 from 1; `has_observation_key_upstr` is computed (`lnk_pipeline_access.R:348`) and deliberately not persisted (`lnk_persist_init.R:89`). Latent: CT's alias observations (`CCT`, `ACT`, `CT/RB`) pass the presence filter but never set code 2, because the test is exact (`"CT" %in% x`).
- **The validator already attaches a mid-segment point to its containing segment** (`R/lnk_habitat_validate.R:874-895`: segment starting within 1 m wins, else `s.drm <= o.m < s.urm`), so `n_obs` / `n_unattached` hold. But its buffered capture enumerates segments by start (`.lnk_hv_buffered`, lines 690-703) and the attached segment's flags move with the merged gradient, so `share_spawning` / `share_rearing` move with segmentation; the roxygen claims at lines 43-44 (99 % on a boundary) and 53-55 ("does not depend on segmentation") are wrong.
- **Cheap probe (local fwapg, `bcfishobs.observations`, unfiltered):** province-wide 81,264 observation positions → 40,159 top-per-species-per-line positions (49 % kept). Per group 21–75 % kept: ELKR 2,269 → 601 (26 %), BULK 1,253 → 682 (54 %), PARS 764 → 361 (47 %), LKEL 201 (sparse). A kept position that coincides with an FWA line start, a crossing or a gradient break removes no segment, so segment counts are question 1's measurement, not this ratio.
- **The config knob pattern** is `.lnk_config_pipeline_check()` (`R/lnk_config.R:386`): closed-set keys checked at manifest load (`discharge_source`, `cabd_additions_barriers`), absent = bcfishpass's behaviour. `config.yaml` is in `config_hash`, so provenance records the knob with no new log column.
- **Before states on m4's dev schemas:** `fresh_default` holds PARS, LKEL, FINA, PCEA at `21e0fea2` (post-#326) and `fresh` the 11-group `bcfishpass` cross-section at the same code, but a persist replaces a group's rows, so an AFTER build into either schema would destroy its own BEFORE (plan review). Both states are therefore built here into scratch schemas, all four groups each way, on one pinned fresh: PARS 4.2 and LKEL 1.4 min make the rebuild cheap. The #326 harness (`data-raw/logs/segmentation_326/run_phase4.sh`: quiet-DB gate, `LNK_GUARD_DOWNSTREAM=warn`, retry once, status TSV; `breaks_diff.R`, `habitat_diff_segments.R`, `default_diff.sh`) is the measurement template. The recompute's downstream-dam post-condition fails in a dev schema lacking the downstream groups (PARS; BULK, ELKR), after its work has committed, so "failed only on the post-condition" is the pass rule and minutes come from the status TSV, not `log_recompute`.
- **Question 3 needs FISS absence sites**, which come from the private `knowledge` repo through `hv_fiss_absences()` in `data-raw/habitat_validate_inputs.R` (`LNK_KNOWLEDGE_DIR`). Visits with fish are bcfishobs locations. If the dir is unset on the measuring host, the bias is measured on observation sites against all segments and the absence side is reported as not measured.

## Decided at the gate (recommended at the parked approval, 2026-10-28; the operator confirms or changes them at resume)

1. **Knob:** `pipeline: observation_breaks:` with values `all` (every position, what bcfishpass does; absent means `all`) and `top_per_species` (the top observation per `(blue_line_key, species_code)`). `default/config.yaml` sets `top_per_species`; `bcfishpass/config.yaml` omits it. Checked at manifest load like `discharge_source`.
2. **Per `species_code` literally.** CT's aliases (`CCT`, `ACT`, `CT/RB`) each keep their own top, for simplicity: the access test is exact (`"CT" %in% x`, `R/lnk_pipeline_access.R:363`), so alias observations never set code 2 for CT today, and their extra breaks change nothing. Collapsing aliases, or making the reader see them, is a separate change to the access reader (recorded in `readers_code2.md`, out of scope).
3. **Groups:** PARS (resident-only), LKEL (sparse, salmon + residents), BULK (salmon + residents, heavily surveyed), ELKR (heaviest reduction, BT / WCT). Four groups, `default` BEFORE into `zz396_default_pre` (main, worktree) and AFTER into `zz396_default_post` (branch, worktree), same fresh; `bcfishpass` AFTER for BULK and PARS into `fresh`, proved unchanged against the committed `segmentation_326/round2/*_breaks.csv` and README counts (BULK 42,989; PARS 43,776), since the AFTER build overwrites round 2's rows.
4. **Question 5 (tributary redundancy)** is counted in Phase 1 and removed only if material (operator's call on the number; the issue's own bar). The count alone needs no code.
5. **The "options if bias is still material"** (inherit the parent gradient; no observation breaks) are not built here; Phase 4's number is reported and the choice goes back to the issue.
