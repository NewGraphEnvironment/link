## The direction rule (holds)

The rule holds. Each part was checked against the code:

- **Inputs are the same in both builds.** Barriers come from staged tables (crossings, gradient, falls, user-definite, subsurface). They are built in prepare, which runs before any break. `.lnk_sql_locate()` locates them on `fwa_stream_networks_sp`, not on link's segments. Lifts (`barrier_overrides`) count observations point against point. The walk reads `<schema>.observations` (every record), never `observations_breaks`, and `observations_breaks` has no other reader. At model time the views read the persist `barriers`, which hold the groups persisted so far in that schema. `run.sh` runs each group's BEFORE and AFTER back to back, so both schemas hold the same groups at each step. The branch's R diff changes nothing the build reads apart from the knob (`lnk_habitat_validate.R` is not on the build path).
- **The walk reads only the start.** `frs_network_features()` passes `(blk, downstream_route_measure, wscode_ltree, localcode_ltree)`. The 10-argument `fwa_upstream` and `fwa_downstream` pass the start as `upstream_route_measure_a` too. Base streams are FWA linear features (`.lnk_pipeline_prep_network()`), and breaks only split them. Every piece is at least 1 cm long, so its BEFORE and AFTER segments lie in one FWA feature and carry the same wscode and localcode.
- **Monotone in the start.** On the same line, a record is upstream when `drm_b > s OR |s - drm_b| <= 1`, that is `drm_b >= s - 1`. A barrier is downstream when `b < s OR |s - b| <= 1`, that is `b <= s + 1`. Every ltree branch (tributaries, side channels, the `wscode = localcode` case, and `fwa_downstream`'s criterion 2) reads only the codes, so it is **constant** within a feature, not just monotone. `access = blocked ? 0 : observed ? 2 : 1`. As the start falls, `blocked` can only go TRUE to FALSE and `observed` FALSE to TRUE, so access can only rise. The merge, `CASE WHEN sc = 0 THEN 0 WHEN t = 2 THEN 2 ELSE 1`, combines two functions of the start that are monotone in the same direction (`t = 2` iff observed and not blocked at model time), so it is monotone as well.
- **Implementation (`pre_post_diff.R`).** `dir` is the sign of `b.dm - a.dm`, with b as AFTER, and a gap under 1 cm counts as the same start. Segment starts are integers or FWA ends, and a break never cuts within 1 m of an end, so two different starts never fall within 1 cm. Each comparison is the right way round: a lower start rejects `acc_b < acc_a` and FALSE to TRUE; a higher start rejects `acc_b > acc_a` and TRUE to FALSE; the same start rejects any change. `species` is limited to active species and `present` drops absent ones, so `-9` never reaches the comparisons.

The rule has one consequence the round 4 docs get wrong (finding 1).

## Findings

- **[bug, a stated mechanism the code contradicts] `RUNBOOK.md` §2c, the bullet "1 to 2 below a tributary mouth"; `research/observation_breaks.md:90-91` ("1 to 2 further up from a tributary mouth"); `code2_class.sql:5` ("it misses 1 -> 2 below a tributary mouth"); `pre_post_diff.R:18-19` ("across lines the ltree tests take in more of the network the lower the start").** This mechanism cannot occur. The sentence just above it in the RUNBOOK says why: a segment never spans a confluence, so the tributary tests do not change within one.
  - FWA ends a feature at every confluence, and the localcode changes there. For every segment of the feature below a mouth, the tributary's records count as upstream through the ltree clause (`wscode_b > localcode_a AND NOT wscode_b <@ localcode_a`), whatever the segment's start. They also count in both builds.
  - For the segment starting at the confluence, they do **not** count: there `localcode_a` equals the tributary's wscode, so `wscode_b <@ localcode_a` holds ("exclude trib at the same position").
  - So "a segment starting at a confluence where X is recorded up the tributary reads X = 2" is false. And no merge can carry a tributary's 2 up the line, because a merge never crosses the feature end at the mouth.
  - Round 4's finding 1, which this text answers, was wrong: its worked case puts a tributary mouth at 400 inside one FWA segment [0, 1000], which FWA cannot hold.
  - What this changes: drop the bullet and the research clause. Drop the `code2_class.sql` clause, which presents the pre-build estimate as an undercount for a reason that does not exist. Reword the script header to say the ltree tests are constant within a piece. On the rule, `km_acc_1_to_2_elsewhere` should come out about 0 (only a lower start near some top of X on the line can turn 1 into 2). A large value there needs explaining; it is not a confirmation.

- **[fragile, a control that cannot fail by exit code] `pre_post_diff.R:159-167`.** The script stops on bad overlap coverage, but on a violation it only calls `message()` and exits 0. Yet its header says "`n_violation` must be 0". There is also a second fault: `n_violation` is computed **after** `write.csv()`, so the CSV has no `n_violation` column, while the message says "see n_violation in pre_post_diff.csv". The three components are in the CSV, so nothing is lost, but anyone checking the named column, or the exit status, will not find the failure. Fix: compute `n_violation` before writing, and `stop()` after writing when it is above 0. Related, minor: a NULL `acc` or `hb` on a moved start makes `acc_b < acc_a` NULL, so the piece is silently not counted. For active species after the merge these columns are never NULL, so this is latent. `IS DISTINCT FROM`-style handling, or a count of NULL pieces, would close it.

- **[fragile, doc] `research/observation_breaks.md:29-31`** still says "the counts are an upper bound, since an FWA end or other cut … already turns the species". Round 4 corrected `exact_set.sql`'s header to "the count is the rule's own size, not a bound": released breaks and kept positions within 1 m of an FWA end make the rule keep too few. The research doc names the first of these in the same sentence and still calls the counts an upper bound. Make it match the header.

Nothing else. The rest of RUNBOOK §2c is right as written: the 1 m arithmetic, the start-rise mechanisms, the recompute keeping a prior 2, and "near-exact, not exact". So are the README index lines and the `exact_set.sql` and `code2_class.sql` headers, apart from the clause in finding 1.
