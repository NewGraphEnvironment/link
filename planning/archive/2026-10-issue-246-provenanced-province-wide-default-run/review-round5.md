- **[severity: bug, prose]** CLAUDE.md:22, research/study_area_run.md:61 and :237 (also planning/active/findings.md:225) — "median 0.68 min per group" is not this run's measurement. It is the median of **63 prior recompute times from earlier runs**, which `recompute_order()` (data-raw/study_area_run.sh:1196) prints *before* the recompute starts, as the default for groups with no recorded time: `ordering 63 known WSG time(s) longest-first (median 0.68 min for the rest)` (data-raw/logs/provincial_246/run.log:84). Re-deriving it from the earlier `*_recompute.log` files gives 63 groups, median 0.68. This run's own times, from `data-raw/logs/study_area_run/20261017_004619_recompute.log` (`[wsg_recompute_one] XXXX recomputed in N min`, 241 lines): **median 2.00 min**, quartiles 1.13 / 3.18, max 16.24, sum 597 min (/4 = 149, which matches the 154 min wall clock at -j4). Only 52 of 241 groups took under 1 min. The number feeds the claim that "the recompute is now the long pole", and #274 and #250 will be sized from it, so it understates per-group cost about threefold. findings.md's "longest groups several minutes" is also low: the max is 16.2 min.

- **[severity: fragile, prose]** R/lnk_pipeline_pscis_build.R:404-409 (the new SQL comment), and planning/active/findings.md "Branch A first, as bcfishpass's `ON CONFLICT DO NOTHING` keeps it" — the stated bcfp mechanism is wrong. In bcfp (`model/01_access/pscis/sql/04_pscis.sql` at the local checkout f8db4b9), both branches sit in **one** INSERT (`referenced_combined` = A UNION ALL B), sorted `ORDER BY linear_feature_id, downstream_route_measure, distance_to_stream` before `ON CONFLICT DO NOTHING`. There is no "first INSERT" between A and B, and no branch precedence: the row kept is the one with the lowest linear_feature_id, then measure, then distance. Both branches in bcfp also carry `lut.modelled_crossing_id`. Today's output is unaffected. Of the two xref rows that set both ids, KITR 203838's modelled crossing 8501815 is on lfid 84042066, the same lfid the xref names, so both branches give the same row. ATNA 203324's modelled crossing 1000400002 is not in `fresh.modelled_stream_crossings`, so only Branch B emits. I checked both by running the new SELECT read-only against fwapg: one row each. But if an xref row ever names a modelled crossing whose lfid differs from its `linear_feature_id`, link keeps A and bcfp keeps whichever sorts first, and the comment tells a reader they match. The code is valid either way. Fix the comment, or order by bcfp's keys to get parity.

- **[severity: fragile, prose]** CLAUDE.md:21 "**One failed group skips the recompute for every group** (#348): the coverage gate exits before it." — the quantifier is too broad. The gate (data-raw/study_area_run.sh ~1396-1407) exits only when a run group has **no rows at all** in `<schema>.streams`. A failed group with rows from an earlier run passes it, as the driver's own NOTE says ("any rows they show above are from an EARLIER run"), and the recompute then runs. In this run it held because KITR and UPET had no earlier rows. Say "a failed group with no earlier rows in the schema".
