- **[severity: bug]** scripts/update_hosts.sh:141-144 — round 1's fix sets `dependencies = TRUE` for every package except link, so fresh is now installed with `pak::pkg_install(..., dependencies = TRUE)`. In pak, `TRUE` means "required plus optional and development dependencies"; the previous call left it at pak's default `NA` (hard dependencies only). fresh's `Suggests:` carries `gq` (with `Remotes: NewGraphEnvironment/gq`, a private repo), `tmap (>= 4.0)`, `bookdown`, `mirai`, `mockery` and others. So every fresh install now also resolves and installs all of fresh's Suggests, including a private GitHub remote. On a host whose GitHub token pak cannot use (m1, per CLAUDE.md 2026-11-02) the whole `pkg_install` fails, so fresh is not updated. Where it does succeed it pulls tmap's whole spatial stack onto the hosts. The value the fix wanted for fresh is `NA` (or the argument left out). The test pins the wrong literal (`dependencies = TRUE` in test-update_hosts.R).
  - **Inside a previous fix?** yes (fix 3)
  - **Rule:** code-check-r.md "pak Behavior"

- **[severity: fragile]** scripts/update_hosts.sh:146-149, 266-268 — both of fix 3's guards report through ssh's exit status: install_pak's `FATAL: … RemoteSha` exit 1 and the new after-install check `[ "$got" = '$FRESH_SHA' ] || { …; exit 1; }`. `on_host` runs them with a plain `ssh "$1" "$2"`, and the driver acts on that exit under `set -e`. Over Tailscale SSH to a Mac (m1 and m4; the repo records this at #376), ssh exits 0 whatever the remote command returned. So when fresh has been put back at another pin, the FATAL prints to stderr and the script carries on and finishes as if fresh were pinned. That is the one case the re-check exists to catch, and nothing downstream of it in this script would notice. The guard has to gate on what the remote prints (e.g. echo a sentinel only on success and test the captured output), as `study_area_remote.sh`'s `remote_run` already does.
  - **Inside a previous fix?** yes (fix 3)
  - **Rule:** code-check-shell.md "Over Tailscale SSH to a Mac, `ssh` exits 0 whatever the remote command returned" ; code-check.md "A guard that fails toward pass"

- **[severity: fragile]** R/lnk_log.R:1325-1330 (`.lnk_bcfp_log_current()` db tier) — two problems:
  - **It reads the timestamp in the session's zone, not the server's.** `date_completed AT TIME ZONE current_setting('TimeZone')` interprets a `timestamp without time zone` in the session's zone. RPostgres sets that zone itself on connect: measured here, `current_setting('TimeZone')` is `UTC` while the server's `reset_val` is `Etc/UTC`. So the comment's "read in the server's zone" does not hold. On a reference server whose default zone is not UTC, a wall-clock `date_completed` is stored shifted by the zone offset (7 or 8 h). Evidence that it is wall-clock: the ledger's hand-copied `bcfishpass.log` value `2026-04-28 23:17` falls in the documented Tuesday 19:00–23:00 PDT window only as PDT. A db-tier `log.bcfp_date_completed` would then disagree with the ledger and env tiers' value for the same build. That field exists to identify the build by its completion time (#266).
  - **NULLs sort first.** `ORDER BY date_completed DESC` puts NULLs first in Postgres, so a LINEAR row with no `date_completed` would be chosen as "newest" ahead of every completed build. It needs `NULLS LAST`.
  - **Inside a previous fix?** no
  - **Rule:** code-check-r.md "Postgres row order is never fixed unless the query fixes it, so a pick, a float sum and a presence check can each depend on it"

- **[severity: fragile]** data-raw/study_area_run.sh:1270-1281 with 1498-1522 — the new pre-spend gate makes every run with cloud hosts pass `--refresh-primitives`, which reloads the dispatcher minutes before launch. A persistent worker (`--workers=`) does not reload at prep. So on any run with both workers and cloud hosts, the worker's PSCIS/CABD content md5 (and its observations version, if bchamp moved) will differ from the freshly reloaded dispatcher's. `compare_inputs` then refuses the run, but only in `preflight_hosts`, after the droplets are spun and prepped and paid for. Workers are reachable before any spend (their ssh, `system_identifier` and schema checks already run pre-spend), so comparing worker and dispatcher loads can happen in `preflight_local`, and nothing does it there.
  - **`--preflight-only` is caught too.** The printed advice `--preflight-only --cy-workspaces=job1,job2,job3` now always fails this gate unless `--refresh-primitives` is added. That makes a "pre-flight only" call run an ~8-minute write-side reload of the dispatcher's primitives.
  - **Inside a previous fix?** no (fix 2 is inside `compare_inputs`, which is correct; this is the gate pairing around it)

- **[severity: fragile]** data-raw/fwapg_load_capture.sh:58-68 — `2> >(tee "$TRACE" >&2)` runs `tee` asynchronously, and bash does not wait for a process substitution. The script then reads `$TRACE` with `artifact_record.R --fwa-trace` without waiting on that `tee`. The last trace lines can still be in `tee`'s buffer at that point, and those are the last objects `load.sh` fetched. Any of them missing are silently not recorded: the read-back counts only the URLs that were parsed. Add `wait $!` after the load (bash ≥ 4.4), or write stderr to the file directly and `cat` it to the terminal after. (Not yet run against a real load, as noted.)
