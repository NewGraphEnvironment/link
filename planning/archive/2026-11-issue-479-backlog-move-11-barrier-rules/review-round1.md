## Findings

- **[severity: bug]** R/lnk_barrier_overrides.R:204-205 (with R/lnk_lift_rules.R:117 and inst/extdata/configs/dictionary_parameters_barrier_lifts.csv) — a lift rule whose `observation_species` is blank lifts nothing, silently. `read.csv()` reads a blank cell in a mixed character column as `""` (and `read_as: text` reads every blank as `""`), so `obs_sp_str` is `""`, not `NA`; `strsplit("", ";")[[1]]` is `character(0)`, and `paste0("'", character(0), "'", collapse = ", ")` returns `"''"`, so the SQL becomes `o.species_code IN ('')`, which matches no record. No error, zero lifts, and the evidence row's `observation_species` is `""`. The dictionary documents the default for a blank cell as "the row's own species_code", and `.lnk_lift_rules()`'s lift_floor check treats blank as the own species (`is.na(lst) || !nzchar(trimws(lst))`), so the validator and the vocabulary accept a rule that the runner turns into a no-op. Same code path for a `parameters_fresh` row (pre-existing there), but the new lifts table advertises the default. Treat `""` like `NA` in `lnk_barrier_overrides()` (or normalise blanks to NA in `.lnk_lift_rules()`).
  - **Rule:** code-check-r.md "`paste()` with a zero-length argument returns length ONE, not zero" ; code-check-r.md "Cross-function consistency for label/string normalization"

- **[severity: fragile]** R/lnk_lift_rules.R:61 vs R/lnk_barrier_overrides.R:110 — `.lnk_lift_rules()` accepts any non-empty rule name, but `lnk_barrier_overrides()` refuses a name outside `^[A-Za-z0-9_.-]+$`. A lifts table with a rule named e.g. `salmon 2` passes load and `lnk_vocabulary_resolve()` (so the run's log row opens and the token resolves) and then stops in `lnk_pipeline_prepare()` mid-build. The roxygen of `.lnk_lift_rules()` says its refusals happen "at load, so lnk_vocabulary_resolve() refuses before a run's log row opens"; this one does not. Apply the same pattern in `.lnk_lift_rules()`.
  - **Rule:** code-check-r.md "Cross-function consistency for label/string normalization"

- **[severity: fragile]** data-raw/schema_consolidate.R:240-244, 598 — the new guard covers only "source has `lift_rule`, destination lacks it". The reverse (destination migrated, so `lift_rule text NOT NULL` in its key; source evidence table built before 0.93.0, without the column) is not refused: `lift_rule` is a destination-only column, so the shared-column COPY inserts NULL into a NOT NULL key column and the evidence COPY fails, after step 3.5 has already deleted the bucket's rows from every destination persist table. The bucket's overrides then copy but its evidence does not, and the destination is left with lifts and no evidence until the source is migrated and re-copied. The file's own comment for the log-table PK check names exactly this outcome ("failing at its COPY would leave this bucket's persist rows already deleted here"). Refuse before the DELETE when the destination carries `lift_rule` and the source does not (or, more generally, when a destination-only column is NOT NULL without a default).
  - **Rule:** code-check.md "A guard's scope, escape hatches, and remedies"

- **[severity: fragile]** R/lnk_barrier_rules.R:67-73, 240 — a `pscis_assessment` row is joined with `LEFT JOIN ... ON c.crossing_source = 'PSCIS' AND ...`, so every non-PSCIS crossing (and every PSCIS crossing with no assessment row) sees all `pa.*` columns as NULL. A row with `operator = is_null` on a `pscis_assessment` column and `applies_to = *` (or any scope including CABD or MODELLED_CROSSINGS) therefore marks every dam and modelled crossing as a human-made barrier. Validation does not refuse that scope for that source, and the result is a plausible-looking barrier set, not an error. Refuse `source_table = pscis_assessment` with an `applies_to` other than `PSCIS`.
  - **Rule:** code-check.md "A guard's scope, escape hatches, and remedies"
