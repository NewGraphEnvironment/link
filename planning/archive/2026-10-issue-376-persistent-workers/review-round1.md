## Findings

- **[severity: bug]** data-raw/study_area_hosts.sh:439-443 (`host_drop_partials`) and data-raw/schema_consolidate.R:768-797 (step 5 source cleanup, now applied to a persistent host) — both delete a group's rows from **every BASE TABLE in `$SCHEMA` that has a `watershed_group_code` column**, which in schema `fresh` (the persist schema of `--config=bcfishpass`, the driver's default config) includes the snapshot primitives, not just persist output. The statement `host_drop_partials` would run, generated read-only against the local `fresh`:
  ```
  DELETE FROM fresh.crossings_vw_bcfp        WHERE watershed_group_code = ANY ('{ADMS}'::text[])
  DELETE FROM fresh.modelled_stream_crossings WHERE watershed_group_code = ANY ('{ADMS}'::text[])
  DELETE FROM fresh.streams_vw_bcfp           WHERE watershed_group_code = ANY ('{ADMS}'::text[])
  … plus the 13 persist tables
  ```
  `fresh.modelled_stream_crossings` is loaded by `snapshot_bcfp.sh` and is what `.lnk_crossings_union()` builds crossings from; `streams_vw_bcfp` / `crossings_vw_bcfp` are the bcfp reference snapshot. On a burned cypher this never mattered. On a worker — "used by other sessions", whose prep "reloads no shared data" — every consolidated group (step 5, `copied_tables` = the src∩dest wgc table list) and every dropped partial group loses its modelled crossings and bcfp reference rows **on the worker**, permanently. The worker's next run (or any other session there) then models those groups with no modelled crossings and passes the vintage gate, which reads load stamps, not rows: silently wrong output. In the other direction, consolidate's step 3/4 replaces the **dispatcher's** `fresh.modelled_stream_crossings` / `streams_vw_bcfp` rows for the bucket with the worker's copy, whose vintage the worker never refreshes (cyphers re-snapshot in prep, workers do not), so the dispatcher's primitives and compare reference become mixed-vintage per group. Same mechanism, smaller blast: step 5 also deletes the worker's `log`/`log_recompute` rows for the bucket's groups from **every** run, not just this one (the source SELECT and DELETE are filtered on group only), so a worker's own build history for those groups is moved off it. `preflight_worker_rows` checks only `streams` / `streams_mapping_code`, so none of this is refused. Fix direction: restrict both the drop and (for a worker source) the consolidate table set to the persist tables link writes (e.g. the `lnk_persist_init` table set), or refuse a worker run whose `$SCHEMA` holds non-persist wgc tables; and scope worker-side log deletes to `run_uid`.

- **[severity: security]** data-raw/study_area_remote.sh:125-134 (`remote_redact_targets`) — redaction replaces only the literal `--workers=` target string, but what ssh writes into the run's logs is often not that string. For a `user@host` target (the charset admits `@`), ssh's own errors name the host part alone (`ssh: connect to host <host> port 22: …`, `Connection to <host> closed by remote host.`), which the whole-token match cannot see; for an ssh-config alias, ssh prints the resolved `HostName` (e.g. a MagicDNS FQDN), not the alias. Those errors land in committed evidence files: `remote_run` merges ssh stderr into `${TS}_reach_<w>.log`, `${TS}_prep_<w>.log`, `${TS}_vintage_<w>.log`, `${TS}_autoinstall_<w>.log`; the leg's `2>&1` puts it in `${TS}_run_<w>.log`; and `consolidate_remote` returns ssh stderr in `$err`, which schema_consolidate.R:668 pastes into the consolidate log on a source-copy failure. Only IPv4 literals are caught by the other pattern. The failure cases (unreachable, dropped link) are exactly the runs whose logs get committed for diagnosis. Fix direction: also redact the host part of a `user@host` target and the `ssh -G <target>` `hostname` value for each worker.
